## Subjects beat the keys (twice) + one authoring typo

1. **ch4-T2 — Standup Market Hub I cannot fit an Astrahus.** The key said
   60 blocks/hr, derived via a drive-script `edit_fit` add that bypassed
   hull legality. Both arms ran validate and caught the rejection; correct
   answer 20 blocks/hr + the illegality. Key corrected.
2. **fr3-B — most mids on a T1 frigate is a three-way tie** (Griffin,
   Heron, Vigil at 5). Key said Griffin alone; the full-arm subject's SQL
   enumeration was right. Key corrected.
3. **ch4-T3 — armor EHP is 9.0M → 30 min** (key prose said "9.9M / 33 min"
   — an authoring typo; the same key line's 29.25M total already implied
   9.0M). Subjects' 30 min graded correct.

Also folded in: ch3-T2/T3 tolerance — the key derivation webbed the Rifter
with a meta web at fixed state (74.8 / then web-free 94.2/35.7); both arms
independently gave the Punisher a Web II in his open mid and kept webs
resident through T3 (81.4 / 111.4/37.8). Same verdicts; the subjects'
reading of "he's webbing me the whole fight" was arguably the more
faithful one.

## Incident: session limit + silent server restart

Mid-run, the account hit its session usage limit (reset 02:40 UTC); six
subjects died mid-turn and were resumed by re-sending the turn after the
window. All six completed correctly post-resume. The same window also
**restarted the shared MCP server process** — fit registry wiped, id
counter reset — which produced a natural experiment in the ch2 pair
(both arms' resident Vedmaks were lost):

- **l2/ch2**: its stale fit_id no longer existed → **loud failure** →
  re-imported, noted "engine state reset (new id f8)" in its provenance
  line, and hit the key exactly (1.0 dps applied / 0.1%).
- **full/ch2**: its stale fit_id `f1` had been **re-assigned** to another
  subject's Thanatos → applied_dps silently returned fighter numbers (raw
  1563, ~7% application). The subject correctly detected the
  inconsistency (panel said 909), refused to stand behind the number, and
  cross-checked SDE range/tracking — exemplary honesty — but misattributed
  the anomaly to an "applied-model bug on disintegrators". Verified
  post-eval: not an engine bug (fresh Vedmak → turrets, 908.9 raw →
  1.0 applied, exactly the key).

Same failure, two outcomes: **loud staleness recovers; silent aliasing
breeds a confident wrong story.** Product fixes queued (below).

## Systematic findings → product fixes

1. **Damage-cap panel shape invites misreads.** Three of four structure
   subjects initially flattened `incoming_dps_cap {shield: 14.4M, armor:
   5k, hull: 5k}` into "5,000 per layer". The full-arm subject
   self-corrected via SQL at T3; the l2 subject, with no second source,
   carried the error into its bash-timeline answer (60 min shield vs the
   true 7.5). Fix: when a layer's cap equals its full raw HP (i.e. no
   practical cap), report it as uncapped instead of printing a huge
   number that reads like a typo'd cap.
2. **Silent fit_id aliasing across server restarts.** Fix twofold:
   (a) echo the ship/fit name in every fit-scoped response
   (`applied_dps`, `graph`, `module_attrs`, `versus`, …) so a wrong
   resolve is visible in one glance; (b) salt fit ids per server boot so
   a stale handle can never silently resolve after a restart.
3. **Drake uniform-vs-Guristas direction (both arms).** Both T1 answers
   got 51,419 vs Guristas right but described uniform EHP as *lower*
   (key: uniform 53,212 is higher — the kin hole outweighs the EM/therm
   hardeners against Guristas). A comparative-direction slip, not a
   computation error; candidate for one traps.md line ("say which way the
   profile moved the number — check both panels, don't narrate").
4. **l2only completeness gap on data-layer questions.** l2/ch5 missed the
   Glorified mutaplasmid tier (best roll 18,000 vs 18,750) because tier
   enumeration is layer-1 data. It labeled its method and stayed
   internally consistent — degradation honesty held; completeness is the
   cost of dropping layer 1. Working as designed.
5. **Arm-design note:** the engine ships its own staticdata sqlite, so an
   l2only session can still answer enumeration questions by querying the
   engine's db (l2/fr3 did, labeled it, and was right). The l2only arm
   can't fully remove data access — only layer-1 *parts*. Fine for
   product (it's real layer-2 capability), worth remembering for eval
   design.
6. **Judgment variance is real but bounded.** ch3-T3: identical engine
   numbers, opposite recommendations (full: "7 km Barrage is safest";
   l2: "stay at 2 km with Fusion"). Both argued from real tradeoffs; the
   shared floor is that neither invented numbers.

Also observed working as intended: heat-spaced EFT layouts survived
edit round-trips in both arms (fr2-C); the ability toggle, class-tube
legality, spool band/ramp, projection falloff, versus damage-pattern
re-weighting, T3D modes, metaliminal storms (including its real cap
penalty — spot-verified post-run), and the alpha_blocked closure all
produced key-exact numbers under fresh questions.
