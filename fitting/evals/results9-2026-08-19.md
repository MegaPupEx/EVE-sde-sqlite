# Eval generation 9 — cost by layer need (2026-08-19)

Design in `questions9.md`: 15 subjects x 3 turns, split into three arms by
which layer the T1 question needs — **layer 1 only** (raw SDE lookup),
**layer 2 only** (fit math on a supplied fit), **both** (lookup feeding fit
math). Every subject then gets:

- **T2** — a follow-up on the same topic (warm context, fits still resident)
- **T3** — an unrelated question in a warm session

T3 is deliberately a *question another arm already answered cold as its T1*,
so the same question is measured twice: once at the start of a session and
once late in one. The L1 arm's T3 is the L2-5 align question; the L2 and both
arms' T3 is the L1-2 blueprint question.

Cost is the deliverable. Answers were read for sanity but not graded against
pinned keys this round.

## Headline

Three numbers carry the round. **Cross-layer questions cost 2.3x a
single-layer one and the excess is rounds, not context.** **Layer-1 lookups
cost the same as engine work today (418k vs 403k)** — the anomaly the
`eve-sde` server is built to fix. And **a warm session makes an unrelated
question 1.4-2.7x *more* expensive than asking it cold**, because accumulated
history is re-read on every round of a question it has nothing to do with.

Run total: **21.0M billed tokens across 44 turns**, ~1.9 h wall clock.

## Run configuration

- Subjects: sonnet, spawned via the Agent tool (multi-turn needs Agent +
  SendMessage, which **inherits the session's reasoning effort** rather than
  pinning medium the way the workflow orchestrator does — so these numbers sit
  slightly above a true medium-effort product run).
- Stack: eve-fitting MCP + both skills; layer-1 access by raw SQL.
- **The new `eve-sde` MCP server is NOT live in this run.** It is registered
  in `.mcp.json`, but a session reads that file at startup, so these figures
  are the **baseline** the with-server run gets compared against.

## Findings

### 1. Needing both layers costs ~2.3x, and it is not additive

T1 means: **layer 1 only 418k, layer 2 only 403k, both 924k**. Additive would
be ~821k. The gap is visible in rounds, not in context: 9.6 and 9.0 rounds for
the single-layer arms against **16.4** for the cross-layer arm. A cross-layer
question is not "one lookup then one calculation" — it turns into a candidate
loop. B-1 spent 29 tool uses building and comparing four hardener variants;
B-4 spent 22 building rig variants. The lookup tells you what to try; the
engine tells you which one won; and the model iterates between them.

### 2. Layer 1 costs the same as layer 2 per question — which is the bug

418k vs 403k, within 4%. That is not what a "just look it up" layer should
cost. It happens because layer-1 answers are produced by hand-written
exploratory SQL: L1-1 took **21 SQL calls over 14 rounds** to answer how much
cargo two haulers hold; L1-4 took 13 rounds for one attribute. This is exactly
the cost the `eve-sde` MCP server exists to remove, and **418k / 9.6 rounds is
the number the with-server rerun has to beat**.

### 3. The follow-up turn is the cheapest thing in a session

T2 mean **299k against T1's 582k** — roughly half, and in the layer-1 arm a
quarter (131k, 2.6 rounds). The answer is already in context or one call away
from a resident fit. The floor case is B-4's T2: **77k, one round, zero tool
calls**, because the navigation stats it needed had been pulled in T1 and were
still in context. Server-side fit residency is doing real work here.

### 4. A warm session makes an *unrelated* question MORE expensive, not less

This is the counter-intuitive result and the one that matters most for the
product. Two questions were each asked twice — cold as one subject's T1, and
warm as another subject's T3:

| question | cold (as T1) | warm (as T3) | ratio |
|---|---|---|---|
| Rifter blueprint minerals | **219k** / 5 rounds / 48k ctx | 402k (layer-2 arm) | 1.8x |
| Rifter blueprint minerals | **219k** | 584k (both arm) | 2.7x |
| Stabber align time | **299k** / 7 rounds / 46k ctx | 419k (layer-1 arm) | 1.4x |

Rounds barely move (5 -> 7, 7 -> 7); context per round grows 48k -> 63k -> 86k.
Cost is rounds x context, and a warm session inflates the second factor without
reducing the first — the accumulated history is irrelevant to the new question
but gets re-read on every round of it. **Session length is a cost multiplier on
every later question, regardless of topic.**

### 5. Context accretion is the lever, and tool output volume drives it

Mean context: T1 56k -> T2 61k -> T3 72k, reaching **118k** in the cross-layer
arm. Every stat panel, SQL result set and sweep table stays resident for the
rest of the session. Finding 4 is a direct consequence: reducing what tools
return is worth more than reducing how often they are called, because returned
bytes are paid once per call and then again on every subsequent round forever.

### 6. Fit-legality checking held

Two of the supplied fits were illegal by my error — the Drake prompt carried 7
launchers on a 6-hardpoint hull, the Rupture prompt 5 turrets on 4. B-1 and
B-4 each caught their own against the validator and said so rather than
answering around it. That is the gen-8 router line working on prompts it was
never tuned for.

## Caveats

- **Effort.** Multi-turn requires Agent + SendMessage, which inherits the
  session's reasoning effort rather than pinning medium the way the workflow
  orchestrator does. These figures sit **above** a true medium-effort product
  run. Within-run comparisons are valid; absolute numbers are an upper bound.
- **B-3's turns merged.** Its T3 relay arrived mid-T2, so it answered both
  questions inside one turn (labelled `T2+3`). That row is excluded from the
  per-turn means and kept in the arm total.
- Answers were sanity-read, not graded against pinned keys. This round measures
  cost only.
