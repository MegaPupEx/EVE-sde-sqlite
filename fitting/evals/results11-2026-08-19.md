# Eval generation 11 — the list-shaped query tool (2026-08-19)

Gen-10 found that `query` was designed around batching that nobody used: 22 of
24 calls sent exactly one statement. The diagnosis was the placement hierarchy
one level down — a docstring asking for batching does not change behavior, the
tool's **shape** does. So the parameter changed from a SQL string to a list:

    query(sql: str)            ->  query(statements: list[str])

The schema now advertises `{"type":"array","items":{"type":"string"}}`, which
makes a single query the awkward case and multiples the natural one. A bare
string is still accepted — refusing it would cost the very round the change is
meant to save — but comes back with a nudge toward the list form.

Same five subjects, same five questions verbatim, same three-turn shape, with
T3 (the Stabber align question) as the pure layer-2 control.

## Did the shape change work? Partly, and not where it mattered

| | gen-10 (string) | gen-11 (list) |
|---|---|---|
| `query` calls sampled | 24 | 35 |
| mean statements per call | 1.1 | **1.2** |
| calls sending one statement | 22 (92%) | 29 (83%) |
| calls sending several | 2 (8%) | **6 (17%)** |

The multi-statement share roughly doubled — the schema did move behavior where
the docstring had not, which is the hierarchy holding. But 83% of calls still
send a single statement, so the lever is still mostly untapped, and **the cost
did not follow**: opening questions went 281k -> 360k, in the wrong direction.

## Why batching was the wrong lever

The reason is visible once you look at what the statements are. SDE lookups are
a **dependency chain**: you need the typeID before you can query its attributes,
and you need the attribute's unitID before you can read its value. You cannot
batch a query whose text depends on the previous result. Asking for a list of
statements only helps for genuinely independent lookups, which are the minority.

The tool that already collapses that chain server-side is `attrs` — name ->
typeID -> attributes -> unit correction, one call. It was used **4 times in
gen-10 and 0 times in gen-11**, against 35 `query` calls. Subjects reach for the
general-purpose escape hatch and hand-walk the chain rather than take the
specific tool that does it in one round.

That is the real finding of this generation: **the win is not in batching
independent queries, it is in higher-level tools that collapse a dependency
chain — and the one we have is being ignored.** The next experiment is
discoverability and scope of `attrs` versus `query`, not another parameter
shape.

## The noise floor, again

The layer-2 control — the align question, which no SDE change can touch — read
420k / 494k / 372k across the three generations, a ±18% swing on a slice that
should be flat. Every cost difference claimed here sits inside that band.
Opening questions went 418k -> 281k -> 360k; none of those gaps is separable
from the control's own movement at n=5.

## Caveats

- **Harness confound.** Gen-11 ran in fresh headless `claude -p` sessions
  (the in-session server held a stale schema and did not respawn after being
  killed), where gens 9 and 10 ran as in-session subagents. Context per round
  differs (T1 mean context 48.6k / 44.7k / 51.0k), so **cross-generation cost
  comparison is confounded**. The batching and tool-choice measurements are
  taken within gen-11 and are not.
- Layer 1 is now entirely on the server: **zero Bash calls** across all five
  gen-11 sessions, against 49 in gen-9.
- n=5, three turns each. Answers were spot-checked and agree across all three
  generations (Drake recharge 1400 s, Rifter blueprint 32k/6k/2.5k/500,
  Veldspar 40 Trit/m3, Iteron 5,800 vs Bestower 4,800 m3).
