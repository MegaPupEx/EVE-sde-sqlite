# Run 3 — 2026-08-17: multi-turn session costs (the "what's the damage" test)

Twelve persistent Sonnet sessions, three turns each, four arms × three
replicas with unique questions. After each answer the same session got the
next question. Purpose: measure what each *subsequent* prompt costs in
tokens and time, since a real chat is a session, not twelve cold starts.

Arms: **F** layered fitting with related follow-ups (fit → swap → external
effect); **F0** the same shapes, fit-sim only (no skill); **S** SDE-only
lookups (eve-sde skill + database, no engine); **M** layered with **both**
layers available and each turn a completely unrelated question.

**Methodology**: the harness reports a cumulative token counter per
session (turn marginals = deltas) and per-turn wall-clock. Caveats:
tokens are full agentic transcript (input+output over the tool loop);
durations include the model's own writing time *and* a ~10–20 s engine
cold-boot per `drive.py` invocation that a production registered MCP
server would not pay (it stays warm); no reasoning-effort control exists
on subagents (Sonnet default, not "medium").

## Findings

1. **Turn 1 is the whole cliff.** Marginal fitting turns run 8–18k
   (median ~11k) against 38–82k first turns — the skill read, the tool
   orientation and the fit import all amortize. A ten-question fitting
   conversation is roughly `t1 + 9 × ~12k ≈ 170k` transcript tokens, not
   `10 × 60k = 600k`.
2. **Unrelated questions do NOT reset the meter.** The M arm's second and
   third turns (completely new topics, new fits) cost the same ~10–17k as
   the F arm's *related* follow-ups. The warm context — skills read,
   tool patterns established — carries across topics; only the fit
   itself is new work. This is the strongest argument that the product
   (one long chat) is affordable.
3. **Fitting vs SDE: ~2× on turn 1, ~2–3× on marginals.** SDE follow-ups
   are ~6k and 15–130 s; fitting follow-ups ~8–18k and 160–540 s. The
   user's guess was right — fitting is the most expensive thing — but
   the gap is smaller than the cold-start numbers implied, and it's
   *latency*, not tokens, where fitting really hurts today.
4. **Latency is engine boots + answer length, not thinking.** Every
   `drive.py` invocation cold-boots pyfa (~10–20 s); follow-up turns that
   batched everything into one script ran fast (M1 t2: 40 s), turns that
   iterated invocations ran 300–500 s. A production registered MCP server
   never pays this — the harness exaggerates production latency badly.
   Long prose answers add generation seconds on every turn.
5. **The cheap turn can be the wrong turn.** The two cheapest fitting
   turns in the whole run were sim-only F02's 1.9k-token black-hole
   answer — **zero tool calls, answered from memory, wrong on 4 of 5
   claims** (black holes worsen agility, boost missile velocity, extend
   lock range — it said the opposite) — and F01's neut turn, which
   claimed **lasers use no cap**. The layered arm answered both questions
   correctly by computing them (F2: `set_env`, +11.3k; F1: projection,
   +10.1k). ~10k marginal tokens is what "actually checking" costs; the
   discipline that forces the check lives in the skill.
6. **The layered stack out-validated the engine — and fixed it.** M3
   caught my 4-mid Omen Navy Issue (3-mid hull) from SDE data and
   correctly reported that `validate_fit` had passed it; M1 caught a
   4-low Gila the same way. Root cause: eos `getSlotsUsed` compares
   `mod.slot is type` (enum identity) and EFT-built modules carry plain
   ints — **rack overflow had never been checked**. Fixed in `_problems`
   (count by slot value) + pinned in the smoke test, commit 4431a2e.
   Both test fits were my authoring errors that the broken check had
   "validated" — a full loop: harness error → subject catches it via
   layer 1 → engine bug found → fixed → pinned.
7. Quality held across turns in the layered arms (M1's tick-quantized
   plate verdict, M2's booster side-effect math joining both layers, F1's
   AAR cap analysis). One waste pattern to fix: M3's turn 2 **re-pasted
   its entire turn-1 answer** (+27.6k marginal); F3/F03's turn-2 spikes
   (~28–30k) were full re-audits of a one-module swap.

## Reduction priorities (ranked by this data)

1. **Run the engine as a persistent MCP server in production** (it
   already is, when registered via `.mcp.json`) — eliminates the
   dominant latency term. For harness realism, a `drive.py --serve` mode
   is the analogue. Biggest speed win, zero token cost.
2. **Conversation-economy rules in the skill router** (landed as a
   result of this run): follow-ups answer the delta, never re-paste or
   re-audit settled turns; batch all engine calls for a question into
   one script; reuse resident fits. Targets the 28k outliers and the
   re-paste pattern — worth ~10–15k on the worst turns.
3. **Answer-length discipline** — fitting answers run thorough past
   usefulness; shorter answers cut both output tokens and seconds on
   every single turn.
4. `get_stats` panels (~260 tok) and schemas (~1.4k standing) are NOT
   where the tokens go — no action needed there yet. A `sections` filter
   stays a v2 nice-to-have.

Correctness sidebar (not this run's focus, graded lightly): layered arms
6/6 on the trap-bearing third turns; sim-only 4/6 with the two memory
failures above; S arm 9/9 turns correct with proper layer discipline
(base-hull labels, ESI pointer for prices, packagedVolume, kspace filter).
