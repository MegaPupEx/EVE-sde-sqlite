## Misses and dings (all minor)

- **C-axis repetition, twice** (A2, A3): numbers appear in a table and
  again in prose. The answer-economy rule says each number once; both
  answers also ran ~10% over the review budget. Not wrong, just longer
  than they need to be — same failure shape the rules were written for,
  now the residual one.
- **Self-reported call counts drift from harness counts** (A2 reported
  12 mcp; harness measured 10 tool uses). Self-report footers are
  approximate; use harness counters for accounting.

## What key preparation caught before launch (the run's real yield)

- **Engine bug: sqlite thread affinity.** Preparing A2's key through the
  live session server crashed it: eos SQLAlchemy objects are
  thread-bound and the MCP SDK dispatches tools to arbitrary worker
  threads — a long-lived server eventually splits two calls across
  threads and dies (first trigger: an import touching saveddata
  `overrides`). The smoke test never caught it because its client
  happens to single-thread dispatch. Fixed by pinning every tool body
  to one dedicated engine thread (re-entrant — tools call tools;
  a naive submit self-deadlocks, which the first fix attempt did).
- **Docs bug: wrong table names for layer 1.** The router/T15 recipe
  pointed at `mutaplasmids`/`mutaplasmidAttributes` — those are the
  *engine db's* names; layer 1 stores the bands as JSON in
  `dynamicItemAttributes`. Fixed before launch; A1's subject then
  found the data in layer 1 without stumbling.

## Cost read for the product question

A "hard" composition question costs the same order as any fitting
question: the tools bound the engine work (ms per calc server-side),
SQL bounds the enumeration, and the token bill is dominated — as in
run 3 — by the fixed session overhead, not by the question's
combinatorial size. The failure mode to watch is not cost but
discipline, and the discipline held: every number cited its layer, the
one impossible question was called impossible, and the one illegal fit
was called illegal.
